Decisions to test before implementation

Can a workspace administrator read Finance?

Compare automatic access with an explicit, audited join. Define whether an administrator can grant themselves access. A settings role alone must not leave this ambiguous.

Walkthrough: a workspace admin who is not in Finance tries to open a payroll issue.

What happens when a bot’s human leaves?

Retain fail-closed behavior for personal agents. Separately decide whether durable CI belongs to the workspace and how its steward, credentials and grants transfer.

Walkthrough: Alice leaves while the release bot has an active token and two running sessions.

Is a project ever a separate sharing boundary?

The draft keeps today’s rule: projects inherit team access. If clients must see one project only, compare a dedicated team with a fully specified project-grant model, including docs, labels, members, search and issue moves.

Walkthrough: an external reviewer should see one project but none of the team’s other work or metadata.

Which actions count as editing work?

Confirm the capability matrix for issue deletion, project archival, labels and bot provisioning. Avoid adding a new role for every action before the common Viewer / Editor distinction is understood.

Walkthrough: a team Editor tries to delete a project, invite a person and create their own bot.

A bounded next research round

Run these four scenarios with three people who would administer or use lll. Ask them to predict access before using the mockup. Record the surprises, agree on one permission matrix and offboarding policy, then turn those into adversarial acceptance cases before migrating data.

Keep the first implementation small: explicit workspace administration, per-team Viewer / Editor membership, personal bots with bounded grants, and sessions with no independent authority. Project ACLs, nested organizations, custom roles and durable service-bot ownership remain separate decisions.
